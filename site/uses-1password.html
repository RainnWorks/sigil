Use case · provider #1

Sigil for 1Password

Your project already keeps its dev secrets in a 1Password item. Sigil gates the op calls that read them, so every access waits for a tap on your phone, and not one script has to change.

The op flow -> Why this is one of many
One use case, not the whole product

1Password is the first provider Sigil ships, not the thing Sigil is. Underneath, Sigil is a generic gate: hold a command, get an approval, inject a credential, run it. The op shim is one integration and the 1Password provider is one source. The same gate is built to take a sigil run wrapper and a Bitwarden or env-file provider next.

This page is the concrete version: exactly which op commands get gated, what your phone shows, and how a rowm project wires it up.

Secrets stay where they are

Nothing moves out of 1Password. A project keeps its dev secrets in one item, and its tools keep reading that item with op. Sigil sits in between.

A rowm service keeps its environment in a single 1Password item, say Engineering/.env, with fields for the database URL, the API keys, and the production AWS access key. The dev launcher, the test runner, agents, and the 1Password SSH agent all resolve those values through op at run time, so nothing sensitive is ever written to disk.

Sigil registers a 1Password service-account token as the account credential. The token arrives once over stdin, never argv, and is stored encrypted under a key the Mac cannot unwrap on its own. From then on, the token is the thing an approval releases; the resolved secret values are never held by the daemon at all.

sigil account add
# the token is read from stdin, never the command line
$ op service-account create sigil-rowm --vault Engineering | \
    sigil account add "Rowm work" --provider 1password

  ✓ credential sealed   key held on Tom's iPhone
  ✓ vaults reachable    Engineering, Personal
  nothing decrypts here until an approval arrives

What gets gated

The shim sits earlier on PATH than the real op, so any call any tool makes routes through Sigil. Teammates without the shim get vanilla op, and nothing about the repo changes.

op callwhat it resolveson your phone
op read "op://Engineering/AWS-prod/access-key"a single fieldREAD SECRET, the reference and the one field
op item get ".env" --vault Engineering --format jsona whole itemREAD ITEM, the item and its field names
op run --env-file=.env.op -- pnpm devan env block for a child processRUN, the command and its env template
ssh git@github.coma signature, via the 1Password SSH agentSIGN, the key label, host, and challenge

The read-a-field versus get-the-item distinction is an op detail carried in the intercepted argv; the approval protocol never learns it. Your phone sees a provider-blind reference and a display hint, which is why the same sheet works for a field read, an item, an op run block, and an SSH signature without knowing anything about 1Password.

One call, from prompt to value

A single gated op read, from an unchanged caller to the secret on stdout. This is the generic round trip with 1Password filled in.

  1. op shimThe dev launcher runs op read "op://Engineering/AWS-prod/access-key". The shim forwards argv, cwd, and stdin over the local socket, byte-for-byte compatible with real op.
  2. daemonParses the op:// reference into a provider-blind request, loads the encrypted service-account token for that account, computes risk (a production vault, a first-seen process), and queues a sealed request. Fires the content-free push.
  3. phoneShows READ SECRET, the reference with AWS-prod leading, the process chain, the working directory, and a gauge counting to expiry. You slide to approve.
  4. daemonUnwraps the key, decrypts the one token, and spawns op with the token in the child's environment. The op child resolves the field and streams it straight onto the caller's stdout. No value enters daemon memory. The token is zeroed.
  5. launcherReceives the access key exactly as if the Mac prompt had been clicked. The audit log records the account, item, process, and cwd, never the value.

A dev session fires many of these. Approving "for this session" holds the unwrapped token in RAM as a lease, scoped to the caller fingerprint, the item, and the request type, until a short TTL zeroes it. The next op run --env-file that starts your server reuses the lease and injects its whole env block without another tap.

More providers, honestly not yet

1Password is the only provider that resolves a secret today. The seam it plugs into is generic and already in the core, which is why the next providers are fills rather than forks.

The SecretProvider trait defines exactly what a provider does: name a stable id, describe the secrets a command will resolve for the approval screen, inject a credential and run the child, and enumerate what a credential can serve at setup. 1Password fills it with op and a service-account token. Bitwarden, AWS Secrets Manager, Doppler, and a plain env-file are the next fills of the same trait.

None of those four resolve a secret yet. When they do, they inherit the pairing ceremony, the approval sheet, the leases, the transport ladder, and the hostile-relay proof unchanged, because none of that layer knows which provider answered.
