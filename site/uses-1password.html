Use case · provider #1

Sigil for 1Password

Your project already keeps its dev secrets in a 1Password item. Sigil gates the op calls that read them, so every access waits for a tap on your phone, and not one script has to change.

The op flow -> Why this is one of many
One use case, not the whole product

1Password is one provider Sigil ships, not the thing Sigil is. Underneath, Sigil is a generic gate: hold a command, get an approval, inject whatever the matching rule seals, run it. The op rule is one integration and the 1Password provider is one source. The same gate already runs any command you write a rule for, and takes a plaintext env-file or sealed inline env values as sources instead.

This page is the concrete version: exactly which op commands get gated, what your phone shows, and how a rowm project wires it up.

Secrets stay where they are

Nothing moves out of 1Password. A project keeps its dev secrets in one item, and its tools keep reading that item with op. Sigil sits in between.

A rowm service keeps its environment in a single 1Password item, say Engineering/.env, with fields for the database URL, the API keys, and the production AWS access key. The dev launcher, the test runner, agents, and the 1Password SSH agent all resolve those values through op at run time, so nothing sensitive is ever written to disk.

Sigil holds none of your 1Password credentials. This is worth being blunt about, because a gate that quietly took custody of your vault token would be a worse deal than the one you already have. op is what Sigil calls a plain gate: a rule decides which op invocations must be approved, and on approval Sigil runs the real op binary, which authenticates itself exactly as it did before. No token is registered with Sigil, none is stored, and none is injected. What an approval releases is the command, not a credential.

Setting it up is therefore one rule, not a credential ceremony. The rule names the command and, optionally, whether one approval may leave a window open for a burst of work.

sigil-config add
# one rule. no token changes hands.
$ sigil-config add op --provider 1password --leasable --lease-max 900

  ✓ configured op
    provider  1password
    lease     leasable(900s)
    the running daemon applies it within a couple of seconds, then:
    sigil op <args>  (or: sigil shim add op)

If you do want Sigil to hold a value, that is a different provider. sigil-config source env set seals KEY=VALUE pairs under the threshold split and injects them into the approved command. Those are the values the trust model's ciphertext-at-rest claims are about; op's own token is not among them.

What gets gated

The shim sits earlier on PATH than the real op, so any call any tool makes routes through Sigil. Teammates without the shim get vanilla op, and nothing about the repo changes.

op callwhat it resolveson your phone
op read "op://Engineering/AWS-prod/access-key"a single field, resolved by op itselfREAD SECRET, the reference and the one field
op item get ".env" --vault Engineering --format jsona whole item, resolved by op itselfREAD SECRET, the item and its path segments
op run --env-file=.env.op -- pnpm devan env block op builds for a child processREAD SECRET, the argv that will run
ssh git@github.coma signature from a key Sigil's own agent servesSSH SIGNATURE, the key label, host, and challenge

The read-a-field versus get-the-item distinction is an op detail carried in the intercepted argv; the approval protocol never learns it. Your phone sees a provider-blind reference and a display hint, which is why the same sheet works for a field read, an item, an op run block, and an SSH signature without knowing anything about 1Password.

One call, from prompt to value

A single gated op read, from an unchanged caller to the secret on stdout. This is the generic round trip with 1Password filled in.

  1. op shimThe dev launcher runs op read "op://Engineering/AWS-prod/access-key". The shim forwards argv, cwd, and stdin over the local socket, byte-for-byte compatible with real op.
  2. daemonMatches the argv against the rules. No match is a refusal. The op rule matches, so the daemon derives a provider-blind reference from the op:// path for display, notes whether this rule may open a window, and queues a sealed request. Fires the content-free push.
  3. phoneShows READ SECRET, the reference with AWS-prod leading, the process chain, the working directory, what the rule covers, and a gauge counting to expiry. You approve with a biometric.
  4. daemonSpawns the real op with the caller's own stdin, stdout, and stderr wired straight to it. op authenticates itself, resolves the field, and writes it onto the caller's stdout. Nothing is injected, because there was nothing to inject, and no secret byte enters daemon memory.
  5. launcherReceives the access key exactly as if the Mac prompt had been clicked. The audit log records the account, item, process, and cwd, never the value.

A dev session fires many of these, so the rule can be marked leasable. Then one approval opens a lease: a window in which anything that rule matches, from this caller chain, runs without asking again. Say that precisely, because it is broader than the one command you approved. For op the window holds nothing at all, only a marker that says "let this rule through", since Sigil has no token to cache. It ends on expiry, on sigil lease revoke, on a daemon restart, or on an edit to the rule, and it is never written to disk. sigil lease list shows every open window with its countdown and its coverage.

More providers, honestly not yet

Three providers exist today and none of them is a hosted vault Sigil talks to on your behalf. The seam is generic and already in the core, which is why the next ones are fills rather than forks.

The SecretProvider trait defines what a provider does: name a stable id, describe for the approval screen what a command will resolve, and run the child with whatever that source injects. 1Password fills it as a plain gate that injects nothing. env-file reads a plaintext KEY=VALUE file you already keep, and is honest that it adds no at-rest protection, only the gate. Sealed env holds KEY=VALUE pairs encrypted under the threshold split, and is the only one whose values Sigil itself decrypts, which it can do only with the phone's per-request share.

A provider that authenticates to a remote vault on your behalf would be a genuinely different shape, because Sigil would then be holding a credential for a service. None of the three below exist yet. When they do, they inherit the pairing ceremony, the approval sheet, the leases, the transport ladder, and the hostile-relay proof unchanged, because none of that layer knows which provider answered.
