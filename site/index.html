Away from the desk, everything behind a prompt stalls

A dev server needs a database URL. An agent needs an API key. A deploy needs a cloud credential. Each is a secret that has to reach the command's environment before it can run, and each raises a biometric prompt on the Mac.

Leave the desk and those prompts sit unanswered. Servers refuse to start, agents block, SSH hangs until you are physically back. Sigil answers the prompt from your phone instead. Two properties keep that from being merely convenient and quietly terrifying.

One gate, and everything plugs into it

Sigil is a small core that does one thing: hold a command, get your approval, inject the approved credential, and run it. Everything else is a plug-in on one of two sides.

Adding Sigil for X = shim a CLI, add a provider, or add an integration the approval your phone shows carries an opaque reference, never provider mechanics

Today one provider is wired (1Password) and one CLI is shimmed (op), plus the SSH agent. The SecretProvider seam, the provider-blind approval protocol, and the injected-credential model all exist in the core now. The second provider, the config-driven shim for any CLI, and the generic sigil run wrapper are in development. They are fills of a seam that is already there, not a rewrite.

The property everything rests on

Approving is not permission. It is the missing half of the cryptography. A provider's credential sits encrypted under a key the Mac never holds. The unwrap key lives on the phone, sealed behind Face ID, and is delivered fresh inside each approval. A stolen daemon is a box of ciphertext.

The second property: no caching, ever. Each approved request resolves live, so a rotated secret is correct on the very next call, and the source stays locked on the Mac. Secret values stream from the provider's child process straight to the caller's file descriptor and never pass through the daemon's memory.

Three parties, three boundaries

The boundary is not a policy. It is what the cryptography structurally allows each party to hold.

  • Your tools receive the one secret they asked for, after approval, and can retain nothing else.
  • The daemon brokers every request but cannot decrypt a credential without a live approval, nor read the secret values it pipes.
  • The phone holds the unwrap key behind a biometric, yet never sees a credential or a resolved secret value.

A request, end to end

The round trip a single request makes, from an unchanged caller to a secret in place. The example is a 1Password read; a sigil run wrapper or an SSH signature travels the identical path, and only the first and last steps differ.

  1. integration → coreA tool runs op item get ".env" --vault "Engineering" --format json. The shim forwards argv, cwd, and the environment request over the local socket, byte-for-byte compatible with the real CLI.
  2. coreRoutes the request to its provider and account, loads that account's encrypted credential, computes a risk level, and queues a signed, sealed request for the phone. Fires the content-free push in parallel.
  3. phoneThe push arrives and wakes a handler that reaches the Mac down the transport ladder, pulls the sealed request, and rewrites the notification on-device. Apple only ever carried "Approval requested".
  4. youGlance: which provider and account, which item or fields, which process, from which directory, how long until it expires. Approve with a biometric, or deny with one tap.
  5. phone → coreOn approve, the biometric unlocks the hardware key, the unwrap key is re-wrapped to this request's ephemeral key, and the signed response returns. Replay-proof: single-use id, monotonic counter, short window.
  6. coreUnwraps the key, decrypts the one credential, and injects it into the child's environment. The child resolves and streams its secrets straight onto the caller's fd, so no value enters daemon memory. Zeroes the key and credential. Writes an audit entry of names and metadata, never values.
  7. integrationThe command runs exactly as if the secret had been present all along. On deny or timeout the shim exits non-zero with a clear stderr line, which is what the caller's error path already expects.

One dev session can fire dozens of requests. Approving "for this session" turns an approval into a lease: the unwrapped credential is held in RAM, scoped to the verified caller fingerprint, command, and request type, until its short TTL expires and it is zeroed. Lockdown, restart, or expiry kills a lease instantly. A lease reduces fatigue; it does not widen the boundary, which is why leases are triple-scoped, TTL-bound, and memory-only.

Friction scales with risk. Deny never does.

The core computes risk from source sensitivity, process novelty, and target host. Risk changes exactly one thing: the shape of the approve control. Refusing is always a single calm tap.

Every approve additionally passes a hardware biometric: the secure element will not release the unwrap key without it, so a stolen unlocked phone still cannot approve. A long press on deny offers "deny and block this process for an hour". Because the approval carries a provider-blind reference and a display hint, the same sheet renders a 1Password read, a wrapped command, or an SSH challenge without knowing any provider's internals.

Deny is framed as the easy, safe default, never an alarm. There is no fear copy anywhere in the product: no shields, no glowing locks, no "you are protected". It is your own tool talking to you.

The transport was never the security layer

Every message on every rung is the same sealed, signed envelope between keys pinned in person at pairing. The phone tries rungs in order; the daemon accepts any of them identically.

1 · LANAt home the app finds the daemon over Bonjour. Zero infrastructure, zero third parties.direct
2 · your endpointA DDNS name or IPv6 address with one forwarded port. Unauthenticated bytes drop on the first frame. Optional; CGNAT blocks it.direct
3 · blind relayA ciphertext mailbox that stores and forwards opaque envelopes it can neither read, forge, nor replay. Self-host the Worker in your own account, or run the protocol-identical Bun server. The daemon connects outbound, so this rung needs no port forwarding.store & forward

What a malicious relay can do, exhaustively

You cannot prove what a remote server runs, so the proof is client-side: the relay is given no role that requires trust. It does not even distribute keys, because pairing is out-of-band by QR, so there is no man-in-the-middle surface at all.

  • Drop or delay traffic. This is a denial of service, and Sigil fails closed: no envelope, no secret.
  • Observe metadata. A pairing-hash mailbox address, timing, and blob sizes. Self-host to keep even that at home.

What it can never do

Its complete behaviour is enumerable, and every entry is neutralized in client code you can read and build.

  • Read a request, or learn a secret name, account, provider, or command.
  • Mint an approval, or replay or reorder a real one.
  • Learn who you are: no accounts, no email, no push token. Mailboxes are a hash of the two paired public keys, self-authenticating and squat-proof.
Claim, code, test

The powerlessness is demonstrated, not asserted. The repository ships a deliberately hostile relay that tampers, replays, forges, and stalls, alongside a client test suite that must reject every attack and fail closed, plus a map from each security claim to the code that enforces it and the test that exercises it. The protocol core and that suite live in crates/sigil-proto and run on every platform, provider or no provider.

One provider today, a registry by design

A provider is a small plug-in that turns an approval into a live secret. The core hands it a resolved request and gets an exit code back; it never sees the values. Swapping the source does not touch the gate, the phone, or the protocol.

The daemon, CLI, and shim are one Rust binary cross-compiled to a standalone, statically linked target per desktop, so installing Sigil is copying a file with no runtime to install. The shim is that same binary invoked through a CLI symlink; op is the first such symlink. The phone is one Expo codebase where the UI layer renders SwiftUI on iOS and Jetpack Compose on Android. All five platforms are committed targets; the seam abstractions exist from the first version so the later ports are fills, not rewrites.
