Away from the desk, everything behind a prompt stalls

All of a project's dev secrets can live in one 1Password item. Every tool that reads them, and every SSH connection through the 1Password agent, raises a biometric prompt on the Mac.

Leave the desk and those prompts sit unanswered. Agents block, dev servers refuse to start, SSH hangs until you are physically back. Latch answers the prompt from your phone instead. Two properties keep that from being merely convenient and quietly terrifying.

The property everything rests on

Approving is not permission. It is the missing half of the cryptography. Service-account tokens sit encrypted under a key the Mac never holds. The unwrap key lives on the phone, sealed behind Face ID, and is delivered fresh inside each approval. A stolen daemon is a box of ciphertext.

The second property: no caching, ever. Each approved request performs a live 1Password read, so a rotated secret is correct on the very next call, and the vault stays locked on the Mac. Secret bytes stream from the op child process straight to the caller's file descriptor and never pass through the daemon's memory.

Three parties, and a boundary each one cannot cross

Your existing tools keep calling op exactly as before. A shim earlier in PATH routes those calls through the daemon; teammates without the shim get vanilla op, so nothing about the repo changes.

A request, end to end

The round trip a single op call makes, from an unchanged caller to a secret on stdout.

  1. launcher → shimA tool runs op item get ".env" --vault "Engineering" --format json. The shim forwards argv, cwd, and stdin over the local socket, byte-for-byte compatible with real op.
  2. daemonRoutes the vault to the right account, loads that account's encrypted token, computes a risk level, and queues a signed, sealed request for the phone. Fires the content-free push in parallel.
  3. phoneThe push arrives and wakes a handler that reaches the Mac down the transport ladder, pulls the sealed request, and rewrites the notification on-device. Apple only ever carried "Approval requested".
  4. youGlance: which account, which item, which fields, which process, from which directory, how long until it expires. Approve with a biometric, or deny with one tap.
  5. phone → daemonOn approve, the biometric unlocks the hardware key, the unwrap key is re-wrapped to this request's ephemeral key, and the signed response returns. Replay-proof: single-use id, monotonic counter, short window.
  6. daemonUnwraps the key, decrypts the one token, spawns op with the token in the child's environment, and splices child stdout onto the caller's fd. Zeroes the key and token. Writes an audit entry of names and metadata, never values.
  7. launcherReceives the item JSON exactly as if the Mac prompt had been clicked. On deny or timeout the shim exits 1 with a clear stderr line, which is what the caller's error path already expects.

One dev session can fire dozens of op calls. Approving "for this session" turns an approval into a lease: the unwrapped token is held in RAM, scoped to the verified caller fingerprint, item, and request type, until its short TTL expires and it is zeroed. Lockdown, restart, or expiry kills a lease instantly. A lease reduces fatigue; it does not widen the boundary, which is why leases are triple-scoped, TTL-bound, and memory-only.

Friction scales with risk. Deny never does.

The daemon computes risk from vault sensitivity, process novelty, and target host. Risk changes exactly one thing: the shape of the approve control. Refusing is always a single calm tap.

Every approve additionally passes a hardware biometric: the secure element will not release the unwrap key without it, so a stolen unlocked phone still cannot approve. A long press on deny offers "deny and block this process for an hour". An SSH request swaps the readout for the key label, target host, and challenge fingerprint, the two things worth verifying.

Deny is framed as the easy, safe default, never an alarm. There is no fear copy anywhere in the product: no shields, no glowing locks, no "you are protected". It is your own tool talking to you.

The transport was never the security layer

Every message on every rung is the same sealed, signed envelope between keys pinned in person at pairing. The phone tries rungs in order; the daemon accepts any of them identically.

1 · LANAt home the app finds the daemon over Bonjour. Zero infrastructure, zero third parties.direct
2 · your endpointA DDNS name or IPv6 address with one forwarded port. Unauthenticated bytes drop on the first frame. Optional; CGNAT blocks it.direct
3 · blind relayA ciphertext mailbox that stores and forwards opaque envelopes it can neither read, forge, nor replay. Self-host the Worker in your own account, or run the protocol-identical Bun server. The daemon connects outbound, so this rung needs no port forwarding.store & forward

What a malicious relay can do, exhaustively

You cannot prove what a remote server runs, so the proof is client-side: the relay is given no role that requires trust. It does not even distribute keys, because pairing is out-of-band by QR, so there is no man-in-the-middle surface at all.

  • Drop or delay traffic. This is a denial of service, and Latch fails closed: no envelope, no secret.
  • Observe metadata. A pairing-hash mailbox address, timing, and blob sizes. Self-host to keep even that at home.

What it can never do

Its complete behaviour is enumerable, and every entry is neutralized in client code you can read and build.

  • Read a request, or learn a secret name, account, or command.
  • Mint an approval, or replay or reorder a real one.
  • Learn who you are: no accounts, no email, no push token. Mailboxes are a hash of the two paired public keys, self-authenticating and squat-proof.
Claim, code, test

The powerlessness is demonstrated, not asserted. The repository ships a deliberately hostile relay that tampers, replays, forges, and stalls, alongside a client test suite that must reject every attack and fail closed, plus a map from each security claim to the code that enforces it and the test that exercises it. The protocol core and that suite live in crates/proto and run on every platform.

One machine, different skins

Nothing in the core is Apple-specific. The crypto, pairing ceremony, leases, relay, and audit model run unchanged everywhere; each platform only supplies its own answer to five seams: keystore, biometric, push, service manager, and socket.

The daemon, CLI, and shim are one Rust binary cross-compiled to a standalone, statically linked target per desktop, so installing Latch is copying a file with no runtime to install. The shim is that same binary invoked through an op symlink. The phone is one Expo codebase where the UI layer renders SwiftUI on iOS and Jetpack Compose on Android. All five platforms are committed targets; the seam abstractions exist from the first version so the later ports are fills, not rewrites.

The daemon speaks plainly

The latch CLI carries the same restraint as the apps: aligned columns, one cobalt accent, semantic green, brass, and rust, no banners. It respects NO_COLOR and non-TTY output.
