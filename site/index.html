Away from the desk, everything behind a prompt stalls

A dev server needs a database URL. An agent needs an API key. A deploy needs a cloud credential. Each is a secret that has to reach the command's environment before it can run, and each raises a biometric prompt on the Mac.

Leave the desk and those prompts sit unanswered. Servers refuse to start, agents block, SSH hangs until you are physically back. Sigil answers the prompt from your phone instead. Two properties keep that from being merely convenient and quietly terrifying.

One gate, and everything plugs into it

Sigil is a small core that does one thing: hold a command, get your approval, inject whatever the matching rule seals, and run it. Everything else is a plug-in on one of two sides.

Adding Sigil for X = shim a CLI, add a provider, or add an integration the approval your phone shows carries an opaque reference, never provider mechanics

Three providers are wired today: op as a plain gate that Sigil never holds a credential for, a plaintext env-file, and inline env values sealed under the threshold split. Any command can be gated by a rule you author, either as sigil <cmd> or through a transparent alias on PATH, and the SSH agent is live. A hosted-vault provider such as Bitwarden or AWS Secrets Manager is a fill of the same SecretProvider seam, not a rewrite, and none of them exist yet.

The property everything rests on

The daemon holds as little as the job allows, and what it does hold is inert. For a command that fetches its own secret, op above all, Sigil holds no credential at all: it gates the call and runs the real binary, which authenticates itself as it always did. For the values you seal into Sigil yourself, the decryption key exists in no one place. It is reassembled per approval from two shares, one on the Mac and one computed inside the phone's Secure Enclave, which never releases it. A stolen daemon is a box of ciphertext and a share that opens nothing.

The second property: no caching, except the window you explicitly open. Each approved request resolves live, so a rotated secret is correct on the very next call. Secret values stream from the gated child process straight to the caller's file descriptor and never pass through the daemon's memory. A lease, when a rule allows one and you choose it, is the one exception, and it is bounded, visible, and revocable.

Three parties, three boundaries

The boundary is not a policy. It is what the cryptography structurally allows each party to hold.

  • Your tools receive the one secret they asked for, after approval, and can retain nothing else.
  • The daemon brokers every request but cannot open a sealed value without a live approval from the phone, nor read the secret bytes it pipes.
  • The phone supplies the other share behind a biometric, yet never holds the key, a credential, or a resolved secret value.

A request, end to end

The round trip a single request makes, from an unchanged caller to a secret in place. The example is a 1Password read; a sigil run wrapper or an SSH signature travels the identical path, and only the first and last steps differ.

  1. integration → coreA tool runs op item get ".env" --vault "Engineering" --format json. The shim forwards argv, cwd, and the environment request over the local socket, byte-for-byte compatible with the real CLI.
  2. coreMatches the argv against the configured rules. No match means refusal. A match names the source, whether the rule may open a lease, and what that rule covers, and the core queues a signed, sealed request carrying exactly that. Fires the content-free push in parallel.
  3. phoneThe push arrives and wakes a handler that reaches the Mac down the transport ladder, pulls the sealed request, and rewrites the notification on-device. Apple only ever carried "Approval requested".
  4. youGlance: which command, which source and account, which process, from which directory, how long until it expires, and whether this rule can be left open for a window. Approve with a biometric, or deny with one tap.
  5. phone → coreOn approve, the biometric gate passes, hardware only, with no passcode fallback. For a sealed source the enclave then computes this request's share; a plain gate needs no share, because there is nothing to open. The signed, sealed response returns. Replay is caught by a single-use request id inside a 150-second freshness window, and then by correlation: the response names the request it answers, and the daemon drops one nothing is waiting for.
  6. coreFor a plain gate, runs the real binary and gets out of the way. For a sealed source, combines the two shares, decrypts only that source's values, injects them into the child's environment, and zeroes the key and the plaintext. Either way the child resolves and streams its output straight onto the caller's fd, so no secret value enters daemon memory. Writes an audit entry of names and metadata, never values.
  7. integrationThe command runs exactly as if the secret had been present all along. On deny or timeout the shim exits non-zero with a clear stderr line, which is what the caller's error path already expects.

One dev session can fire dozens of requests, so a rule may be marked leasable. Then one approval can open a window instead of answering one command, and anything that rule matches runs inside it without asking again. That is a real widening, stated plainly: for a sealed source the unsealed values are held in RAM for the window's duration. What bounds it is that run-once is the default, the daemon clamps the window to the rule's cap whatever the phone asks for, sigil lease list shows every live window with its countdown and what it covers, sigil lease revoke ends one at once, and expiry, a restart, or an edit to the rule kills it. Nothing is written to disk.

Approving is one tap. So is refusing.

The sheet's job is to show you what you are answering: the command, the process chain that led to it, the directory, and what the rule covers. The only thing a rule changes is whether that one tap may also leave a window open behind it.

Every approve passes a biometric on the phone, hardware only: the passcode fallback is disabled, so there is no second route past a failed face or thumb. Be precise about what that buys, because the two paths differ. A plain gate, which is what every op rule is today and therefore the path most people are on, is authorised by that biometric and nothing else, since there is nothing to decrypt. A sealed source additionally needs the phone's Secure Enclave to compute this request's share, an operation nothing else on the device can perform. So the enclave stands behind sealed values specifically, not behind every approval: someone who can pass your biometry on your unlocked phone can approve a plain gate.

Because the approval carries a provider-blind reference and a display hint, the same sheet renders a gated command, a sealed environment injection, or an SSH challenge without knowing any provider's internals.

Deny is framed as the easy, safe default, never an alarm. There is no fear copy anywhere in the product: no shields, no glowing locks, no "you are protected". It is your own tool talking to you.

The transport was never the security layer

Every message on every rung is the same sealed, signed envelope between keys pinned in person at pairing. The phone tries rungs in order; the daemon accepts any of them identically.

1 · LANAt home the app finds the daemon over Bonjour. Zero infrastructure, zero third parties.direct
2 · your endpointA DDNS name or IPv6 address with one forwarded port. Unauthenticated bytes drop on the first frame. Optional; CGNAT blocks it.direct
3 · blind relayA ciphertext mailbox that stores and forwards opaque envelopes it can neither read, forge, nor replay. Self-host the Worker in your own account, or run the protocol-identical Bun server. The daemon connects outbound, so this rung needs no port forwarding.store & forward

What a malicious relay can do, exhaustively

You cannot prove what a remote server runs, so the proof is client-side: the relay is given no role that requires trust. It does not even distribute keys, because pairing is out-of-band by QR, so there is no man-in-the-middle surface at all.

  • Drop or delay traffic. This is a denial of service, and Sigil fails closed: no envelope, no secret.
  • Observe metadata. A pairing-hash mailbox address, timing, and blob sizes. Self-host to keep even that at home.

What it can never do

Its complete behaviour is enumerable, and every entry is neutralized in client code you can read and build.

  • Read a request, or learn a secret name, account, provider, or command.
  • Mint an approval. Replaying a real one is caught by a single-use request id inside a 150-second freshness window, and then by correlation: a response names the request it answers, and one with no live waiter is dropped. The trust model states what that leaves open.
  • Learn who you are: no accounts, no email, no push token. Mailboxes are a hash of the two paired public keys, self-authenticating and squat-proof.
Claim, code, test

The powerlessness is demonstrated, not asserted. The repository ships a deliberately hostile relay that tampers, replays, forges, and stalls, alongside a client test suite that must reject every attack and fail closed, plus a map from each security claim to the code that enforces it and the test that exercises it. The protocol core and that suite live in crates/sigil-proto and run on every platform, provider or no provider.

Three providers today, a registry by design

A provider decides what an approval does. Some hold nothing and simply let the gated command run; others inject values Sigil holds sealed. The core hands a provider a resolved request and gets an exit code back; it never reads the values. Swapping the source does not touch the gate, the phone, or the protocol.

One machine, different skins

Nothing in the core is Apple-specific. The pairing ceremony, leases, relay, provider seam, and audit model run unchanged everywhere; each platform only supplies its own answer to five seams: keystore, biometric, push, service manager, and socket. One thing does not port yet, and it is the interesting one: the threshold share that opens a sealed value is a Secure Enclave key with no Android equivalent written, so Android is a gate-only approver.

The daemon, CLI, and shim are one Rust binary cross-compiled to a standalone, statically linked target per desktop, so installing Sigil is copying a file with no runtime to install. The shim is that same binary invoked through a CLI symlink; op is the first such symlink. The phone is one Expo codebase where the UI layer renders SwiftUI on iOS and Jetpack Compose on Android. All five platforms are committed targets; the seam abstractions exist from the first version so the later ports are fills, not rewrites.

Getting it

No builds are published yet, and this is pre-release: the cryptography has had an independent adversarial review, but the surface is still moving. Read the code before you trust it with anything that matters. First run is a single command that wires the shim, registers the agent, and walks the pairing ceremony.
