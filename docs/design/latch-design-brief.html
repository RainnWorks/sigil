Why this exists

All of Rowm's dev secrets live in one 1Password item. Every tool that needs them, and every SSH connection through the 1Password agent, pops a biometric prompt on the Mac. Away from the desk, those prompts sit unanswered and everything behind them stalls: agents block, dev servers refuse to start, SSH hangs until you are physically back.

Latch replaces the Mac popup with a phone approval. Two ideas make that safe rather than convenient-but-terrifying:

The core property

The daemon at rest cannot produce a single secret. Service-account tokens sit encrypted under a key the Mac does not hold. The unwrap key lives on the phone, sealed behind Face ID, and is delivered fresh inside each approval. Approving is not permission; it is the missing half of the cryptography.

The second idea: no caching, ever. Each approved request performs a live 1Password read via a service account, so a rotated secret is correct on the very next request, and the vault itself stays locked on the Mac. Secret bytes stream from the op child process directly to the caller's file descriptor; they never pass through the daemon's memory.

The system

Five pieces. Your existing tools keep calling op exactly as they do today; a shim earlier in PATH routes those calls through the daemon. Teammates without the shim get vanilla op, so nothing about the monorepo changes.

A request, end to end

  1. launcher → shim The rowm dev launcher runs op item get ".env" --vault "Engineering" --format json. The shim forwards argv, cwd, and stdin over the local socket. Byte-for-byte compatible with real op.
  2. daemon Routes Engineering to the right account via the plaintext vault table, loads that account's encrypted token, computes a risk level, and queues a signed, sealed ApprovalRequest for the phone. Fires the content-free APNs doorbell in parallel.
  3. phone Notification arrives; a service extension reaches the Mac down the transport ladder (LAN, then your endpoint, then the relay), pulls the sealed request, and rewrites the notification body on-device, so Apple only ever carried "Approval requested."
  4. you Glance: which account, which item, which fields, which process, from which directory, how long until it expires. Approve (Face ID) or deny (one tap, always).
  5. phone → daemon On approve, Face ID unlocks the Secure Enclave key, the DEK is re-wrapped to this request's ephemeral key, and the signed response returns over the same direct connection. Replay-proof: single-use request id, monotonic counter, 90-second window.
  6. daemon Unwraps the DEK, decrypts the one SA token, spawns op with the token in the child's env, and splices child stdout onto the caller's fd. Zeroes the DEK and token. Writes an audit entry: names and metadata, never values.
  7. launcher Receives the item JSON exactly as if the Mac popup had been clicked. On deny or timeout the shim exits 1 with a clear stderr line, which is exactly what the launcher's error path already expects.

Leases: approve once, cover the session

One dev session can fire dozens of op calls, and the callers cannot be changed; they think they are running the real CLI. So the caller's identity is derived instead: the daemon reads the true peer pid from the socket, walks the ancestor chain kernel-side, and resolves each ancestor to its executable path and code-signing identity (never raw pids, which recycle). The hash of that chain plus the project root plus the requested scope is the grant key. The daemon verifies all of it itself; a client's claims about its own ancestry are ignored.

Approving with "for this session" turns the approval into a lease: the unwrapped account token is held in RAM only, scoped to that grant key, item, and request type, until the TTL expires, then zeroed. A lease is a leased capability, not a policy flag; the daemon still cannot serve anything outside it without the phone. Lockdown, deny-and-block, restart, or expiry kill a lease instantly, and the phone lists every active lease with a countdown and one-tap revoke.

Spam is also handled before it reaches you: requests with an identical grant key arriving while one is pending coalesce behind it, so one decision settles the whole burst; pushes collapse to "4 approvals waiting"; per-caller rate limits back-pressure anything pathological. Honest limit: a process-tree key reduces fatigue, it does not upgrade the security boundary; same-user malware could imitate a caller during a live lease window, which is exactly why leases are triple-scoped, TTL-bound, and memory-only.

SSH is the same loop with a better ending. The agent socket receives a signature request, the phone shows the key label, target host, and challenge fingerprint, and on approval the daemon fetches the private key, signs in memory, zeroes it, and returns only the signature. SSH clients never see key material at all. In v2 the key moves into the Secure Enclave and never exists outside hardware.

Friction scales with risk; deny never does

The daemon computes risk from vault sensitivity, process novelty, and target host. Risk changes exactly one thing: the shape of the approve control. Deny is always a single calm tap, because refusing must never be harder than allowing.

elevatedProduction vault, or a process seen for the first time, with one reason lineslide to approve
criticalSignature to a production host, bulk readshold 1.5s to approve

Every approve additionally passes Face ID: the Secure Enclave will not release the unwrap key without it, so a stolen unlocked phone still cannot approve. Long-press deny offers "Deny and block claude for 1 hour." An SSH request swaps the readout well for key label, host, and challenge fingerprint, the two things worth verifying.

Android, Windows, Linux: the same machine, different skins

Nothing in the core is Apple-specific. The crypto, envelopes, pairing ceremony, leases, relay, and audit model run unchanged everywhere; each platform only supplies its own answer to five seams. The daemon, CLI, and shim are one Rust codebase cross-compiled to standalone single-file binaries (cargo build --release targets macOS arm64 and x64, Linux arm64 and x64, and Windows x64; the whole desktop install is one binary around half a megabyte, no runtime to install). The phone app is one Expo codebase where @expo/ui renders SwiftUI on iOS and Jetpack Compose on Android.

Trust model

Pairing is the root of trust

At pairing, each device mints Ed25519 signing and X25519 agreement keys inside its own secure hardware. Public keys cross via a QR code rendered locally, confirmed by a six-word fingerprint read off both screens, and are pinned forever after. Every message in both directions is sealed and signed between those pinned keys; a compromised network hop can neither read a request nor forge an approval. The unwrap key (DEK) is delivered to the phone once at pairing, optionally enveloped a second time to the Mac's Secure Enclave for Touch ID approvals, and then erased from the daemon.

The transport ladder

The transport was never the security layer: every message on every rung is the same sealed, signed envelope between keys pinned at pairing. So the phone and the notification extension simply try rungs in order, and the daemon accepts any of them identically.

1 · LANAt home the app finds the daemon over Bonjour. Zero infrastructure, zero third parties.direct
2 · owned endpointA DDNS name, static IP, or IPv6 address with one forwarded port. Safe to expose: unauthenticated bytes are dropped on the first frame and the parser is tiny. Optional purism; CGNAT blocks it.direct
3 · blind relayA ciphertext mailbox: it stores and forwards opaque envelopes it can neither read, forge, nor replay. Self-host the ~100-line Worker in your own Cloudflare account (or run it as a tiny Bun server), or use the shared cloud instance; the trust surface is identical either way: metadata and availability, nothing more. The daemon connects to it outbound over WebSocket, so this rung needs no port forwarding and works from any network.store & forward

What the relay can do at worst: drop or delay traffic, which is a denial of service and therefore fail closed; and observe metadata (pairing id, timing, blob sizes). What it can never do: read a request, learn a secret name, mint an approval, or replay one; the libsodium seal, pinned Ed25519 signatures, and single-use counters hold regardless of who carries the bytes.

Proving the relay powerless. You cannot prove what a remote server runs, so the proof is client-side: the relay is given no role that requires trust. Unlike Signal, it does not even distribute keys; pairing is out-of-band by QR, so there is no man-in-the-middle surface at all. Its complete possible behavior is enumerable (deliver, drop, delay, duplicate, observe sizes and timing) and every entry is neutralized in client code anyone can read and build. The repo ships the evidence: a deliberately hostile relay implementation that tampers, replays, forges, and stalls, with a client test suite that must reject every attack and fail closed, plus a map from each security claim to the code enforcing it and the test exercising it.

Anonymous by construction. The relay has no accounts. A mailbox address is a hash of the two paired public keys, self-authenticating and squat-proof; the relay holds those two pseudonymous keys only to drop unsigned garbage (its check is anti-abuse, never load-bearing; clients verify everything themselves). It learns no name, no email, no Apple identifier: the APNs device token never touches it, because the daemon sends pushes directly to Apple.

What centralization remains, exactly: iOS offers no way to remotely wake an app except APNs, so the doorbell is the one irreducible Apple dependency, and pushing requires the paid Developer Program. Apple sees "Approval requested" and nothing more; the informative notification text is assembled on-device by a service extension that fetches down the same ladder. If the phone has no path to the Mac at all, requests fail closed: approve at the Mac with Touch ID, or let it time out and fall back to vanilla op. Never a bypass.

Distribution: paid Developer Program + TestFlight for the daily build (90-day refresh, real push). Free-account local builds work for v0 in poll-only mode but expire weekly and cannot push. A poll-only mode remains permanently as the graceful floor.

Decisions made along the way

  • Name: Latch (binary latch). The name is the interaction: a request is latched, approving lifts it, lockdown dead-latches. Runners-up: Moor, Quay, Warden.
  • No secret caching: live service-account reads per approval, so rotation is instant and the vault stays locked. Rejected the op-remote startup-cache model.
  • Transport ladder, direct first: LAN, then your own endpoint, then a blind relay (self-hosted Worker/Bun server or a shared cloud instance) that only ever carries sealed envelopes. Mesh VPNs rejected as an unnecessary party; the relay is acceptable because E2E makes it powerless. The daemon sends its own APNs pushes either way.
  • Visible doorbell, not silent push: iOS throttles silent pushes (~5/day, dropped after force-quit); a content-free visible alert is the reliable and honest choice.
  • Either-factor unwrap: phone Face ID by default, Mac Touch ID via a second enclave envelope when enabled; hardened mode deletes the second path.
  • Trust is proven client-side: the relay is anonymous (key-hash mailboxes, no accounts, no APNs token), holds no key-distribution role, and its powerlessness is demonstrated by a hostile-relay test suite shipped in the repo rather than asserted.
  • Leases over per-call approvals: caller identity is a daemon-verified fingerprint (code-signing chain + project root + scope), and a session approval holds the unwrapped token in RAM for the TTL. Identical requests coalesce behind one decision, so a burst costs one glance.
  • Shim exits like real op (code 1, clear stderr) so existing error handling in the monorepo works untouched; opt-in distinct exit codes.
  • Stack: phone = one Expo codebase, @expo/ui rendering SwiftUI on iOS (with expo-glass-effect) and Jetpack Compose on Android; Mac = pure SwiftUI with Liquid Glass (Expo has no macOS target); Linux and Windows get CLI-first config with minimal trays; daemon, CLI, shim = one Rust codebase cross-compiled to standalone binaries for every desktop (~half a MB, no runtime to install; the Keychain ACL and Authenticode caller checks bind to these signed binaries). Bun survives only as the optional relay-server variant.
  • Portability by seams: keystore, biometric, push, service manager, and socket are the only platform-specific layers; crypto, pairing, leases, relay, and the proof suite are shared code everywhere.

To verify before building

  • Current 1Password service-account rate limits and plan quotas (volume here is tiny, but doctor should surface them).
  • Service accounts cannot see built-in Personal/Shared vaults: confirmed platform limit; the account-add flow must probe and warn.
  • Keychain ACL survival across Developer ID re-signs and updates of the daemon binary.
  • APNs collapse-id behavior under rapid multi-request bursts.
  • Notification service extension: 30s budget reliably covers the ladder walk (LAN timeout → endpoint → relay) on cellular.
  • Whether your ISP is CGNAT-free or offers routable IPv6; this decides if rung 2 exists for you (rung 3 works regardless).
  • Durable Object WebSocket hibernation limits for the daemon's long-lived relay connection.
