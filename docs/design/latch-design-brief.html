Why this exists

A secret lives behind a local gate. To read it, a tool pops a biometric prompt on the Mac; every SSH connection through the 1Password agent does the same. Away from the desk, those prompts sit unanswered and everything behind them stalls: agents block, dev servers refuse to start, SSH hangs until you are physically back at the machine.

Sigil moves the gate to your phone. The insight that keeps that safe rather than merely convenient is that Sigil is not really an op tool at all. It is a generic engine: given a command, it gets one phone approval, injects the approved credentials into that command's environment, runs it, and streams the output back. What secret source sits behind the injection, and how a command reaches Sigil in the first place, are both pluggable. 1Password is simply the source that shipped first.

Two properties make phone approval safe:

The core property

The daemon at rest cannot produce a single secret. Provider credentials sit encrypted under a key the Mac does not hold. The unwrap key lives on the phone, sealed behind Face ID, and is delivered fresh inside each approval. Approving is not permission; it is the missing half of the cryptography. A stolen laptop, powered off, yields ciphertext and nothing else.

The second property: secret values never enter the daemon's memory. The daemon injects a credential into a child process (for 1Password, a service-account token, itself a credential and not a resolved secret) and splices that child's stdout and stderr onto the caller's own file descriptors. The resolved secret streams from the child straight to the caller; the daemon brokers the release without ever holding the value. This shapes the whole provider contract, so no future provider can quietly break it.

Layer 1 · Core

The generic machine. Its whole job is: gate a command on a phone, then inject the approved environment into it and run it. It carries the pairing handshake, the sealed and signed protocol, leases, the transport ladder, the keystore seam, risk scoring, the audit log, and lockdown. It has no concept of 1Password or SSH. The protocol types it seals to the phone name no provider: a request carries the raw argv, a list of opaque secret references, and a display hint, never a vault or a field.

Layer 2 · Integrations

How a request enters the core. latch <cmd> is the primitive; the transparent PATH shim is a thin alias to it; the SSH agent is a distinct integration whose event is a signature rather than an injection. Each integration's only job is to turn some external trigger into a core request and hand back the result.

Layer 3 · Providers

Where the secrets come from, behind the SecretProvider trait. A provider parses its own reference syntax for the readout, and injects its credential so the child resolves and streams its own secrets. It never returns a value to the daemon. 1Password ships as provider #1; a direct-injection env-file provider ships as #2 (the reference impl that proves the seam is not op-shaped), and the id-keyed provider registry that dispatches between them is built.

The invocation model shipped

The primary primitive is latch <cmd> [args]. You run latch op read op://... or latch gcloud ...: Sigil looks up the configuration for that command, and if it is configured it pings the phone, injects the configured environment on approval, runs the command, and streams the output. If the command has no configuration, Sigil refuses and tells you to add one. It never runs an unconfigured command ungated, because a silent pass-through would be false security.

Reserved latch verbs (status, pair, daemon, and the rest) always win, so latch run -- <cmd> is the unambiguous escape hatch for a command that collides with a verb.

The shim is now a thin alias shipped

A binary named op (or gcloud, or bw) placed first on PATH exists only for callers that cannot be modified: a launcher that shells out to a bare op item get, a git that reaches the SSH agent, an AI agent that only knows the real command's name. The shim's entire job is to rewrite op ... into latch op ... and forward. It is a transparent alias to the primitive, not a second code path.

The shim is config-driven: latch shim add <cmd> drops a transparent alias binary for any configured command, and every alias (and the latch <cmd> primitive, and latch run --) forwards the same run frame to the daemon, which looks up the command config and gates it. The op alias is the same code path as any other, not a special case.

Fail-safe fallback shipped

When the daemon is down, the shim transparently execs the real underlying tool, so nothing breaks when Sigil is off. When the daemon is up but a request errors at the protocol level, the shim fails closed rather than silently running the tool locally, so a mutating command can never slip past the gate once one exists.

A request, end to end

The round-trip is provider-agnostic. Nothing in it knows the request is about 1Password; swap the provider and every step below is unchanged.

  1. caller → integration A command arrives, whether typed as latch op read ..., intercepted by the shim, or driven by the SSH agent. The integration forwards the argv, the working directory, and the caller's own stdout and stderr descriptors over the local socket.
  2. core The daemon asks the configured provider to describe the command into opaque secret references for the readout, loads the matching account's encrypted credential, computes a risk level, and deposits a signed, sealed request into the phone's relay mailbox slot, alongside the phone's registered push token. The relay reads that token once, rings a content-free doorbell push to Apple on the daemon's behalf, and forgets it.
  3. phone A fixed "Approval requested" alert arrives, nothing more; the phone drains the sealed request waiting for it at the relay.
  4. you Glance: which command, which references, which process, from which directory, how long until it expires. Approve with Face ID, or deny with one tap, always.
  5. phone → core On approve, Face ID unlocks the Secure Enclave key, the unwrap key is sealed to this response inside the audited envelope, and the signed response returns over the same connection. Replay-proof: single-use request id, monotonic per-pairing counter, 90-second window.
  6. core The daemon unwraps the key, decrypts the one credential, and hands it to the provider's run, which spawns the child with the credential in its environment and splices the child's stdout onto the caller's descriptor. The daemon zeroizes the key and credential and writes an audit entry: names and metadata, never values.
  7. caller Receives the output exactly as if the local prompt had been approved. On deny or timeout the integration fails closed with a clear stderr line.

Leases: approve once, cover the session shipped

One dev session can fire dozens of gated calls, and the callers cannot be changed; they think they are running the real tool. So the caller's identity is derived instead: the daemon reads the true peer pid from the socket, walks the ancestor chain kernel-side, and resolves each ancestor to its executable and code-signing identity (never raw pids, which recycle). The hash of that chain plus the project root plus the requested scope is the grant key. The daemon verifies all of it itself; a client's claims about its own ancestry are ignored.

Approving "for this session" turns the approval into a lease: the unwrapped credential is held in RAM only, scoped to that grant key, account, and scope, until the TTL expires, then zeroed. A lease is a leased capability, not a policy flag; the daemon still cannot serve anything outside it without the phone. Lockdown, deny-and-block, restart, or expiry kill a lease instantly, and the phone lists every active lease with a countdown and one-tap revoke.

Spam is handled before it reaches you: requests with an identical grant key arriving while one is pending coalesce behind it, so one decision settles the whole burst; pushes collapse to a count; per-caller rate limits back-pressure anything pathological. Honest limit: a process-tree key reduces fatigue, it does not upgrade the security boundary; same-user malware could imitate a caller during a live lease window, which is exactly why leases are triple-scoped, TTL-bound, and memory-only, and cannot widen their own scope.

The daemon computes risk from source sensitivity, process novelty, and target. Risk changes exactly one thing: the shape of the approve control. Deny is always a single calm tap, because refusing must never be harder than allowing.

Providers: where secrets come from

A provider is a Rust trait with four responsibilities: give a stable id, produce a display hint for a command, describe a command into opaque references for the readout, and run the command with its credential injected so the child streams its own secrets. It never hands a resolved value back to the daemon; that shape is deliberate, so the memory invariant cannot be broken by a careless provider.

The provider registry and a second reference provider are the concrete next step: a second live provider is what turns "the seam is designed" into "the seam is proven." Until then, 1Password is the sole shipping provider and the trait is exercised only by it plus test fakes.

SSH is a distinct integration agent shipped

SSH does not fit the injection model: the event is a signature over a challenge, not an environment full of secrets. So it is a separate integration on the same core. Sigil implements the SSH agent protocol (RFC 9987) itself, advertises your keys, and gates every signature through the identical sealed approval loop. You point SSH_AUTH_SOCK at Sigil's socket; from then on git push and ssh transparently ask the phone. ssh-add -l against the running daemon already lists the served key with its real fingerprint.

Where the private key comes from is a pluggable signer, exactly like a SecretProvider is a pluggable secret source. Sigil is the universal phone-gate regardless of how you hold keys.

The honest three-way trade

You cannot have all three of these at once. Pick two.

The default gives the first and third: keys stay 1Password-managed and signing works while you are away, at the cost of the key transiting daemon RAM for one signature. That transit is the design's most honest residual, and the reason the v2 SE-resident signer exists. Proxying the 1Password desktop agent does not help, because its local biometric popup is the exact wall Sigil exists to escape. There is no protocol hostname in an SSH signature; the destination shown on the phone is a best-effort reverse lookup of the session-bind host key against known_hosts, falling back to the host-key fingerprint, never fabricated.

Trust model

Pairing is the root of trust shipped · 30 MITM proofs

At pairing each device mints Ed25519 signing and X25519 agreement keys inside its own secure hardware. The Mac renders a QR on its own screen; the phone reads it with its camera. That optical channel is authenticated by physics, not cryptography: no network hop sits between a screen and a lens. The QR carries the daemon's real keys plus a 256-bit one-time secret, so only the real phone learns the secret, and the phone's network reply is authenticated by proving possession of it. A network attacker who never saw the QR cannot forge an acceptable reply, so it cannot pass off its own key as the phone's.

A six-word fingerprint read off both screens is the human backstop, computed over the two now-pinned identities: if the daemon ever pinned an attacker's key, the words diverge and the human sees it. Authorizing a pair takes three separate gates, in order: physical presence at the Mac (the QR exists only on its own screen), the six-word SAS comparison above, and only then a fresh Touch ID prompt at the Mac's Secure Enclave, the sole way the DEK can be unwrapped. Declining the SAS bails out before any biometric is even requested, and a same-UID process that only manages to script the SAS confirmation still cannot finish a pairing, because it has no way to satisfy the Enclave's own hardware gate. Once unwrapped, the key is sealed to the phone's pinned key and immediately erased from the daemon; from then on it arrives per-approval from the phone. The whole handshake ships with a hostile-MITM suite of roughly thirty adversarial tests that swap keys, flip tag bits, replay across pairings, skew clocks, and starve the one-time secret, each asserting the handshake fails closed. An independent security review of the SAS-confirm gate, the Secure Enclave DEK wrap, and their ordering found the pairing-security unit sound at the code level: there is no path that delivers the DEK without both a genuine SAS gate and a fresh Enclave-gated biometric (see docs/security-claims.md).

The factor policy: what actually gates a request shipped

An earlier review found that the local control socket was same-UID forgeable: a rogue process running as you could send an approve frame and self-approve, which is exactly the adversary Sigil exists to stop. That finding is closed. At arm time the daemon now resolves an explicit approving factor, in strict order:

phoneA paired phone reachable over a transport. Its sealed, signed approval a same-UID peer cannot forge. The real shipping gate.preferred
biometricA verified hardware Secure Enclave keystore. The unwrap is the biometric.fallback
fail closedNeither of the above: the daemon arms so status and pairing work, but refuses every gated request. Never silently self-approvable.default

The old control-socket self-approval and a dev auto-approve exist only under an explicit --dev-insecure switch, which prints a loud multi-line warning naming the same-UID risk on every start. A real factor always wins over the dev path, so passing the flag on a properly paired daemon does not weaken it.

The transport ladder real relay proven e2e

The transport was never meant to be the security layer: every message on every rung is the same sealed, signed envelope between keys pinned at pairing, so the phone and the daemon can accept whichever rung answers first, identically. The design is direct-first with a blind relay fallback, not a mesh VPN, but only the fallback is built today: every remote approval currently goes over rung 3.

1 · LANAt home the app would find the daemon over Bonjour: zero infrastructure, zero third parties. Not yet built: no mDNS discovery or direct socket exists, so a LAN request still routes through the relay below.planned
2 · owned endpointA DDNS name, static IP, or IPv6 address with one forwarded port, so unauthenticated bytes would drop on the first frame. Optional purism; CGNAT blocks it. Not yet built: no DDNS client or direct transport exists.planned
3 · blind relayA short-lived mailbox: the daemon and phone each deposit and drain opaque envelopes over plain HTTP, in per-mailbox to-phone / to-daemon slots held only in the relay's own process memory (a Durable Object instance, or a Bun Map), never written to disk. Each envelope expires after 180 seconds and is deleted the moment it is read (drain-on-read), so nothing outlives the gap between a deposit and the other side's next poll: no queue, no persisted counter, zero storage at rest. On a phone-bound deposit the relay also rings a content-free APNs doorbell, so the wake-up needs no held connection either. Self-host a small Cloudflare Worker in your own account (or run the Bun variant), or use a shared instance; the trust surface is identical. The daemon reaches this rung over plain outbound HTTP, so it needs no port forwarding and works from any network.HTTP mailbox

Proving the relay powerless. You cannot prove what a remote server runs, so the proof is client-side: the relay is given no role that requires trust. Unlike a prekey server, it does not even distribute keys; pairing is out-of-band by QR, so there is no man-in-the-middle surface at all. Its complete possible behavior is enumerable (deliver, drop, delay, duplicate, observe sizes and timing) and every entry is neutralized in client code anyone can read and build. The repo ships the evidence: a deliberately hostile relay that tampers, replays, forges, reorders, and stalls, with a client suite of fourteen attacks that must each be rejected and fail closed, plus a map from every security claim to the code enforcing it and the test exercising it. That whole loop is proven end-to-end over the real Bun relay, including recovery after the relay restarts mid-flight: nothing is held in a live connection to lose.

Blind by construction; anonymous with one exception. The relay has no accounts. A mailbox address is a hash of the two paired public keys: the relay holds only that hash, never the keys, and never parses the envelopes it carries, so it cannot even attempt to read them. Anti-abuse is purely structural: a size cap, a per-mailbox rate limit, and the 180-second drain-on-read TTL above, so nothing queues past the next poll. Invariant #3 is honestly relaxed here: the one irreducible centralization is now the push doorbell, and the relay runs it, not the daemon. Sigil ships one app to many phones behind one Apple developer identity, and no user's Mac can be trusted to hold the publisher's APNs signing key, so the relay holds that one key and, once per deposit, the depositing phone's push token, just long enough to ring Apple and forget it; the token is never persisted and never leaves that one request. Apple sees a fixed "Approval requested" alert and nothing else: no caller, no command, no account, no reason. An independent security review confirmed the crypto still holds despite this: the relay's new powers let it ring a doorbell, and at worst spam one with content-free noise, but they do not let it read a secret, forge an approval, or learn an outcome (see docs/security-claims.md). If the phone has no path to the relay at all, requests fail closed: approve at the Mac with Touch ID, or let it time out. Never a bypass.

The surfaces

Three renderers over one core. The daemon is the single source of truth; the clients never read its store directly.

The machine interface in progress

The daemon's control socket is the single machine API. The Mac app speaks it directly for live state, runtime control, and event streams, so the CLI and the Mac app are two renderers of one protocol rather than two separate interfaces. Deliberately, this API is read-and-control only. Keystore and configuration mutations (account add, rotate, remove; settings; wipe) stay least-privilege and CLI-only, because the network-exposed daemon must never be able to mutate keys or config. The protocol and its PROTOCOL.md spec are being built now; the Mac app currently runs against a mock pending its socket client.

iOS shipped

Expo SDK 57 on React Native 0.86, with @expo/ui rendering real SwiftUI primitives, Liquid Glass on iOS 26, and native tabs. Dark-first: approvals happen on the couch, in bed, at a bar. The approval sheet, the real pairing rendezvous, and the real relay transport are built and verified end-to-end against the live Rust daemon, with the wire format byte-parity-locked to Rust through shared test vectors and react-native-libsodium for the crypto.

Terminal shipped

The latch CLI carries the same restraint as the apps: aligned columns, one cobalt accent, semantic green, brass, and rust, mono symbols, no banners. Respects NO_COLOR and non-TTY. It is a thin client of the daemon, plus the least-privilege mutations that never leave the CLI.

Mac builds; socket client pending

Calm, terse, factual. It is your own tool talking to you: no fear, no "you're protected", no exclamation marks. The cliches were audited out deliberately: no shields, no hacker green, no glowing padlocks, no AI purple; deny is framed as the easy safe default rather than an alarm.

Decisions log

  • Sigil is any-CLI, not an op tool. The core is a generic gated-exec-with-injection engine; 1Password is provider #1. Three layers (core, integrations, providers) with a hard seam each, so "Sigil for X" is a config, a provider impl, or an integration, never a rewrite.
  • latch <cmd> is the primitive; the shim is a thin alias. Look up config for a command, gate it, inject its env, run it; refuse an unconfigured command rather than run it ungated. The transparent shim collapses to rewriting op ... into latch op ..., existing only for callers that cannot be modified.
  • Name: Sigil (binary and crates stay latch). A sigil is a sealed mark that authorizes: the phone seals an approval, and the six-word SAS is the mark's attestation, the thing a human actually checks before trusting it. Every user-facing surface says Sigil; the CLI you type and the internal crates keep the name latch underneath.
  • No secret caching. Live per-approval reads, so rotation is instant and the source stays locked. The startup-cache model was rejected.
  • Secret values never enter daemon memory. The provider trait injects a credential and streams the child's output to the caller's fds; it is deliberately not a fetch() -> bytes shape, so a provider cannot break the invariant.
  • The unwrap key lives only on the phone. Delivered once at pairing after SAS, optionally enveloped a second time to the Mac Secure Enclave, then erased from the daemon; it returns per-approval. This makes the daemon inert at rest.
  • The factor policy closes the self-approval finding. Phone > biometric > fail-closed; the control-socket and dev auto-approve exist only under a loud --dev-insecure switch, and a real factor always wins over it.
  • SSH is a distinct integration with a pluggable signer. Default is 1Password-fetch (key in RAM one signature, the honest residual); SE-resident, file, and proxy signers follow. The three-way trade is documented, not hidden.
  • Transport ladder, direct first. LAN, then an owned endpoint, then a blind relay carrying only sealed envelopes over plain HTTP deposit and drain. This is not a mesh VPN. The relay rings the content-free APNs doorbell on the daemon's behalf, using the one publisher key it holds; the daemon never talks to Apple itself, and the relay sees a device push token only transiently, per deposit, never stored.
  • Trust is proven client-side, and invariant #3 is honestly relaxed. The relay is blind (key-hash mailboxes, no accounts, never parses an envelope) and holds no key-distribution role, but the v4 doorbell gives it one narrow new power: the shared publisher push key plus a transient per-deposit push token. An independent review confirmed this still cannot read a secret, forge an approval, or learn an outcome; its remaining powerlessness is demonstrated by a hostile-relay suite in the repo rather than asserted.
  • The control socket is the single machine API. The Mac app and CLI are two renderers of it. Keystore and config mutations stay CLI-only and least-privilege, because the network-exposed daemon must never be able to mutate keys or config.
  • Stack. Phone is one Expo codebase (SwiftUI on iOS today, Compose on Android later). Mac is pure SwiftUI with Liquid Glass. Daemon and CLI are one Rust workspace built to a single release binary around half a megabyte, no runtime to install.
